5. TIME ZONES AND TIP-OFF TIMES
==============================================================================
Whether a game rolls over is arithmetic. It rolls when local tip-off
plus the zone's UTC offset crosses midnight, so every zone has a
threshold, and the threshold moves an hour with daylight saving.

zone   standard time (Nov-Mar) daylight time (Mar-Nov)
ET     rolls at 19:00 local    rolls at 20:00 local
CT     rolls at 18:00 local    rolls at 19:00 local
MT     rolls at 17:00 local    rolls at 18:00 local
PT     rolls at 16:00 local    rolls at 17:00 local

This is the part most likely to be misread. The intuition that this
is a west-coast problem holds only under daylight time. Under
standard time -- which is most of the regular season -- an EASTERN
7:00pm tip is already midnight UTC, so a routine 7:00 or 7:30pm start
rolls over in every zone in the league. What survives correct are
afternoon and early-evening games: weekend matinees, holiday noon
games, and 7:00-7:30pm Eastern starts during the daylight-time months
at the very start and end of the season.

7. WHAT ACTUALLY DISPLAYS A WRONG DATE
==============================================================================
Read off scripts/build.py, not guessed. A feature only matters here
if a one-day shift changes what a reader sees.

  latest_game_day (build.py ~3862)
    surfaces at : index.html, 'Most recent officiating crews' heading date
    affected    : YES -- displays the stored date outright, and can also SPLIT one real night across two stored dates, so the module may show only the late half

  date_index / month_day (build.py ~3881)
    surfaces at : index.html, 'On this date' card
    affected    : YES -- a game is indexed under the wrong calendar day, so the card attributes a performance to the day after it happened

  referee_games per-game date (build.py ~3814)
    surfaces at : referee/<slug>/games/, the full game log
    affected    : YES -- every row's date column

  notable games (build.py ~1399, ~1429)
    surfaces at : referee/<slug>/, notable-game tables
    affected    : YES -- the date beside each game

  swings (build.py ~2028, ~2063)
    surfaces at : swings/ and the index swings strip
    affected    : YES -- the date beside each swing

  recent form windows (build.py ~1695-1915)
    surfaces at : index recent-form spotlight, referee recent-form blocks
    affected    : PARTLY -- cal30 is a date window, so a shifted game can cross the boundary, and days_since_last_game is off by one

  era (build.py ~314)
    surfaces at : internal split between the two feeds
    affected    : NO -- derived from the game_id scheme, never from the date

  debuts / farewells (build.py ~2361)
    surfaces at : debuts/ and the index debuts widget
    affected    : NO -- keyed on first_season / last_season, which are season labels. A one-day shift cannot move a game out of its season, so this is NOT affected despite being a date-shaped feature

Note the two NOs. era is keyed on the id scheme and debuts/farewells
on season labels, so neither moves with the date even though both
look like date features from the outside.

WHAT THIS PROBE DOES NOT ESTABLISH
==============================================================================
- No per-game count of misdated games. games.csv.gz has no tip-off
  time, so the totals in section 4 are a fitted estimate with a
  stated residual, not a census.
- The 1993-94..2002-03 ESPN block has no adjacent NBA-scheme season,
  so no rate could be fitted for it. Its Dec-24 counts in section 2
  say it is affected; they do not say by how much.
- Nothing here was re-fetched. Confirming a specific game's real
  local date needs the cdnnba timeActual timestamps, which are in a
  gitignored cache and were not available to this run.
